障害: まず予測だけをaudit表に保存してcommitし、完了時刻が締切60秒前であることを確認してから本番行へ反映する。予測保存の途中で落ちた場合、本番行は触らない。確認済み予測の本番反映と旧行退避は同一本番DB取引。反映前/commit直前にも締切を検査。OS/DBの長期停止中を含めた物理的commit完了時刻の保証はしないが、その場合でも予測自体は締切前に保存済み。forecast_persisted_atが予測証拠時刻、application_checked_atが反映直前の確認時刻であり、混同しない。未確認のaudit行は実績から除外。手動復元では保存した適用後の行と現行行が完全一致する場合だけ旧値に戻し、他処理による変更を消さない。

予測を保存した時刻と本番反映完了時刻は分離: forecast_persisted_at / application_finished_at。後者が締切後ならapplication_before_deadline=falseとlate_applicationを記録し、締切前配信の実績には数えない。計算・予測保存済みでも、OS停止等による本番反映の遅延を防ぐ絶対保証はしていない。

時刻判定はホストのJST壁時計が正確であることを前提とする。時計巻き戻り・誤設定下での実時刻保証はない。反映完了後の記録前に停止した行はapplication_before_deadlineが欠落するため、締切前反映の実績に数えない。独立反証で判明したこの前提を採用し、絶対保証は撤回。12テストがローカル/M4で成功。
